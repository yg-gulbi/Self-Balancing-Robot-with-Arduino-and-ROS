# 조작하지 않았는데 바퀴가 움직였다: RC 입력부터 분리해 확인하기

[English](../../../troubleshooting/major/01-rc-pwm-spikes.md) | [전체 트러블슈팅](../../troubleshooting.md)

> FrSky X8R의 PWM을 모터 제어와 분리해 관찰하고, 배치에 따른 증상 변화와 중립값을 바탕으로 입력 처리 방식을 수정했다. 최종 코드에는 채널별 필터, 데드밴드, 활성화 지속성 검사가 남아 있다.

## 바퀴의 움직임만 보고 제어 게인을 바꿀 수는 없었다

실물 로봇을 구동하는 과정에서 조작 의도와 다르게 바퀴가 순간적으로 움직였다. 처음 보이는 현상은 모터의 움직임이었지만, 그 현상만으로 자세 제어가 잘못되었다고 판단하기는 어려웠다. 수신기가 잘못된 명령을 보내는 경우와 정상 입력을 받은 모터 경로가 잘못 반응하는 경우를 구분해야 했다.

그래서 확인 대상을 **바퀴 움직임에서 Arduino에 들어오는 PWM 펄스폭으로** 옮겼다. 입력 단계에서 신호가 튄다면 자세 제어를 다시 튜닝하기 전에 명령 해석부터 바로잡아야 하기 때문이다.

## 수신기 단독 시험으로 무엇을 보았는가

[수신기 테스터](../../../../firmware/testers/receiver_pwm_test/receiver_pwm_test.ino)는 ODrive 구동 없이 throttle, steering, engage의 펄스폭을 확인할 수 있도록 구성되어 있다. 상승 에지 시간을 저장하고 하강 에지까지의 시간 차를 `micros()`로 계산한다. 출력은 115200 baud에서 약 20 ms 간격으로 다음 열을 제공한다.

```text
throttle_us    steering_us    engage_us
```

이는 **테스터의 출력 열 이름**이다. 당시 측정값을 새로 재현한 로그는 아니다.

이렇게 채널을 나누면 throttle·steering의 변화는 이동 의도와, engage의 변화는 모터 활성화 판단과 연결해 볼 수 있다. 출력 간격은 약 20 ms이므로 모든 펄스의 이상을 빠짐없이 기록하는 장치는 아니지만, 모터 반응과 입력 신호를 분리해 확인할 수 있는 관찰 지점을 만든다.

기존 작업 기록에는 다음 관찰이 남아 있다.

| 확인한 조건 | 기록된 관찰 | 다음 판단 |
| --- | --- | --- |
| Arduino에서 수신기 PWM 확인 | 펄스폭이 갑자기 변하는 현상 확인 | 자세 제어만의 문제로 다룰 수 없음 |
| 배선·수신기 접속 수정 | 접속과 배선 조건을 여러 차례 변경 | 입력 경로의 상태를 따로 확인할 필요 |
| 금속 구조물과 수신기 위치 변경 | 금속 근접 여부에 따라 증상이 달라짐 | 수신기·안테나 배치를 원인 후보로 유지 |
| 알루미늄 포일 적용 | 신호 튐이 오히려 악화 | 포일 적용을 해결책으로 채택할 근거가 없음 |

특히 포일 실험은 예상한 방향으로 개선되지 않은 시도였다. 이 결과는 배치와 주변 전도성 물체가 영향을 준다는 단서였지만, RF 환경과 PWM 배선 노이즈 중 어느 것이 지배적인지는 이 기록만으로 확정할 수 없었다.

## 입력을 그대로 명령으로 쓰지 않도록 바꿨다

최종 대응은 배치·배선 검토와 입력 처리였다. 수신기를 금속 구조물·전력 배선에서 떨어뜨리고 신호선과 GND 귀환선을 가까이 배치하는 방향을 검토했다. 소프트웨어에서는 잡음의 성격에 따라 서로 다른 처리를 넣었다.

| 최종 코드의 처리 | 실제 설정 | 제어 경로에서의 역할 |
| --- | --- | --- |
| throttle·steering 저역통과 필터 | `alpha=0.4` | 짧은 입력 변화가 이동·조향 요구에 바로 반영되는 정도를 완화 |
| engage 저역통과 필터 | `alpha=0.02` | 활성화 신호에 더 강한 평활화 적용 |
| 중립 데드밴드 | 중심에서 편차가 `50 us` 미만이면 0 처리 | 작은 중립 편차를 주행 의도로 해석하지 않음 |
| 활성화 지속성 검사 | 50 ms 주기의 상태 갱신에서 카운터 사용 | 한 번의 판정만으로 활성 상태가 바뀌는 것을 완화 |

필터는 다음과 같이 구현되어 있다.

```cpp
filtered_throttle_pwm = kAlpha_1 * throttle_pwm + (1.0 - kAlpha_1) * filtered_throttle_pwm;
```

throttle과 steering에는 같은 계수를 사용하지만 engage는 더 작은 계수를 사용한다. 조작 응답과 활성화 판단이 요구하는 반응 특성을 구분한 것이다.

지속성 카운터는 판정에 따라 증가·감소하고 `-3~3`으로 제한되며, 0보다 크면 engage 상태로 판단한다. 따라서 “항상 정확히 3회 연속 입력을 받아야 켜진다”는 단순 규칙으로 설명할 수는 없다.

중립값도 무조건 1500 us로 가정하지 않았다. 데드밴드 기준은 throttle 1488 us, steering 1492 us이다. 다만 throttle 정규화식에는 1491 us가 남아 있어 기준이 완전히 통일되어 있지는 않다.

## 바뀐 것은 필터 하나가 아니라 입력에 대한 신뢰 기준이었다

이 작업에서 중요한 구분은 **수신기 값이 존재하는 것**과 **실제 조작 의도로 받아들여도 되는 것**이었다. 중립 부근의 편차, 순간적인 튐, 활성화 신호는 같은 방식으로 처리할 수 없었다.

이를 각각 필터·데드밴드·지속성 검사로 다룬 과정은 입력 신호를 제어기 앞단에서 정제하는 설계로 이어졌다. 금속과 포일에 따른 변화는 하드웨어 조건을 조사할 이유를 주었고, 코드 변경은 남아 있는 입력 변동의 영향을 줄이는 수단이었다.

## 면접에서 확인할 수 있는 근거

**이 사례가 보여주는 작업:** 관찰 지점 분리, 실패한 대응안의 해석, 신호 특성에 따른 입력 처리.

- [receiver_pwm_test.ino](../../../../firmware/testers/receiver_pwm_test/receiver_pwm_test.ino): 펄스폭 측정 방식과 출력 항목.
- [physical_balance_controller.ino](../../../../firmware/physical_balance_controller/physical_balance_controller.ino): `kAlpha_1`, `kAlpha_2`, 데드밴드, engage 카운터.
- [개발 과정](../../development-process.md): 수신기와 배선 조사 배경.

최종 구현은 코드로 확인할 수 있다. 금속·포일 실험 결과는 기존 작업 기록의 관찰이며, 공개된 원시 로그와 전후 스파이크 발생률은 없다. 따라서 “입력 처리와 배치 검토로 대응했다”까지 설명하고, 노이즈가 몇 퍼센트 감소했다고 말하지 않는다.
