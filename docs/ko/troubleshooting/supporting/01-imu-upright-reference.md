# IMU의 0°가 로봇의 직립점은 아니었다

[English](../../../troubleshooting/supporting/01-imu-upright-reference.md) | [전체 트러블슈팅](../../troubleshooting.md)

> 센서 캘리브레이션과 기구의 직립 기준을 구분하고, 최종 자세 계산에 오프셋을 적용했다.

## 계속 보정하는 현상을 게인만으로 다룰 수 없는 이유

IMU가 보고하는 각도와 실제 몸체의 직립 자세가 다르면 제어기는 잘못된 기준점을 향해 계속 복원하려 한다. 기존 작업 기록에서 캘리브레이션과 기준점 관리를 다룬 이유다. 이 현상은 게인을 바꾸기 전에 센서 시작 상태·장착 방향·직립 기준을 함께 확인해야 하는 문제였다.

## 센서 상태와 직립 기준을 따로 확인하도록 구성했다

BNO055 초기화 실패 시 실행을 멈추고, 캘리브레이션 상태를 확인하는 함수와 EEPROM 저장·복원 함수를 준비했다. 이와 별도로 실제 자세 계산에 `imu_angle_offset`을 두었다.

| 코드 경로 | 확인하거나 바꾸는 것 |
| --- | --- |
| `bno.begin()` | 센서가 초기화되는지 확인 |
| `checkIMUCalibration()` | system·gyro·accel·mag 보정 상태 출력 |
| `saveCalibration()` / `loadCalibration()` | 22바이트 보정 데이터 저장·복원 |
| `SetImuAngleOffset()` | 제어에 사용하는 직립 기준 조정 |

센서 보정 데이터와 몸체 직립 오프셋은 같은 값이 아니다. 센서를 보정해도 장착 각도와 기구의 평형점 차이는 별도로 남을 수 있기 때문이다.

## 최종 코드에서 실제로 적용되는 것은 무엇인가

```cpp
float imu_angle_offset = 3.5;
```

자세 계산은 다음과 같다.

```cpp
theta = imu_enabled * (euler_angles.y() + imu_angle_offset);
```

이 식에서 보정 후 0°는 원시 y각이 -3.5°인 지점이다. **이는 코드에서 계산한 기준의 의미이며 실측 자세 로그가 아니다.** 기울기 임계값 검사에도 같은 오프셋을 더한다.

한편 `setup()`의 `loadCalibration()`과 `checkIMUCalibration()` 호출은 주석 처리되어 있다. 저장·복원 함수가 남아 있어도 현재 스케치가 부팅마다 자동 복원과 상태 출력을 수행하는 것은 아니다.

## 기준점을 제어기의 입력 조건으로 다루게 되었다

여기서 남은 설계 판단은 캘리브레이션 상태와 실제 직립점을 분리한 것이다. 오프셋은 시리얼 명령 `r`에 연결되어 자세 게인과 별도로 바꿀 수 있다. 따라서 “복원력이 약한가”와 “복원하려는 기준점이 다른가”를 다른 변수로 조사할 수 있다.

## 면접에서 확인할 수 있는 근거

**이 사례가 보여주는 작업:** 센서 초기화·보정·기구 기준의 구분, 제어 기준점의 명시적 설정.

[최종 제어기](../../../../firmware/physical_balance_controller/physical_balance_controller.ino)의 `setup()`, `checkIMUCalibration()`, `SetImuAngleOffset()`, `BalanceController()`를 연결해 확인할 수 있다. 오프셋 구현은 코드로 검증되지만, 현재 공개 자료에는 동일 자세에서 재부팅 전후 각도를 비교한 로그가 없어 재시작 재현성 개선량까지 입증하지는 않는다.
